# Agent 学习课程体系设计

## 背景与目标

当前 AI 应用常把大量上下文、规范、知识一次性塞进 system prompt，导致上下文爆炸、注意力分散、token 浪费。

本项目希望换一种方式：为 AI 设计一套渐进式课程，让它在实际项目开发任务中实践，逐步成长。核心目标是：

- AI 先自主执行一次任务；
- 将执行经验沉淀为**星序图**；
- 下次遇到同类任务时，直接按星序图执行，更高效、更省 token。

## 核心概念

### 功课系统

chat-core 中的 `chatLoop` 本质上是一个循环进化的机制：

1. 用户请求 = 出题；
2. LLM 推理 + 工具调用 = 做题；
3. 工具执行结果回填 messages = 批改反馈；
4. LLM 看到反馈后调整策略 = 订正；
5. 直到不再需要工具 = 功课完成。

关键点是 messages 数组作为经验累积器，LLM 每轮都站在之前所有尝试的基础上做决策。

### 星序图 vs skill

| | skill | 星序图 |
|---|---|---|
| 层级 | L2 领域（skill-host） | L3 能力（flow-engine） |
| 本质 | 工具/能力包 | 任务流程/剧本 |
| 内容 | 一组可调用的工具定义 | 节点、分支、状态转移 |
| 产生方式 | 人写或外部下载 | AI 从实践中沉淀 |
| 作用 | 提供"手"和"眼" | 提供"做事的步骤" |

关系：星序图执行时可能调用 skill 中的工具；AI 学会一件事之后，把它沉淀成星序图，下次直接复用。

## agent 的架构定位

### agent 与 agent-runtime 的分工

| | agent | agent-runtime |
|---|---|---|
| 本质 | 一个具体的"大脑"实例 | 运行大脑的"环境" |
| 内部 | 5 器官框架 + 职业星序图 | 进程注册、生命周期、通信、调度 |
| 类比 | 一个具体的人（有专长） | 办公室 / 组织架构 |
| 复用单位 | 职业 + 专属星序图 | 运行调度能力 |

L3 层拆成两个包：

- `@xingseq/agent`：单个 agent 大脑；
- `@xingseq/agent-runtime`：多 agent 运行时，让多个 agent 能同时存在、协作、被调度。

### 职业星序图

每个 agent 可以配置一个或多个**职业**，职业就是该 agent 擅长的**星序图集合**：

- 代码审查员：擅长代码审查、风险识别星序图；
- 测试工程师：擅长生成测试用例、执行测试星序图；
- 架构师：擅长模块拆分、接口设计星序图；
- 需求分析师：擅长需求澄清、任务拆解星序图。

不同职业的 agent 通过 agent-runtime 协作：

```
用户任务
  → agent-runtime 调度
  → 选择合适职业的 agent（或创建新实例）
  → agent 调用自己的星序图完成子任务
  → 多个 agent 通过 agent-runtime 通信协作
  → 汇总结果返回
```

### agent 作为 AI 成长引擎

agent 不只是多角色编排器，而是**AI 成长引擎**：

- 管理课程体系；
- 跟踪 AI 学习进度；
- 将学习与实践结合；
- 通过反思机制确保 AI 真正掌握知识。

### 统一入口：所有任务先走大脑

与"简单任务走 chat-core、复杂任务走 agent"的想法不同，这里的设定是：

- **所有任务统一由 agent 处理**；
- 简单任务处理后沉淀为**简单星序图**；
- 复杂任务处理后沉淀为**复杂星序图**；
- **复杂星序图由简单星序图组合而成**，不是每次从头推理。

这样系统会形成一个不断积累的图库：早期 AI 没有沉淀时，每个任务都靠大脑现场推理；随着简单星序图增多，复杂任务可以直接复用已有图作为节点，大脑只负责编排和兜底。

### 角色分工

外部仍保留 5 个角色作为概念层，便于理解和交互；但内部实现会简化：

- **Soul**：学习态度和价值观，把控沉淀边界；
- **Planner**：根据课程进度 + 项目需求，规划"学什么 + 做什么"，也负责判断能否沉淀为星序图；
- **Executor**：触发可靠执行单元完成任务，不再直接维护 loop 细节；
- **Reflector**：做更高层的质量审查（跨步骤、跨任务），日常自检由执行单元内部完成；
- **Coder**：代码相关任务的专项入口，内部同样基于可靠执行单元。

### 可靠执行单元

Executor 和 Reflector 的"执行 + 自检"循环被封装成一个内部单元：

```
Planner 下发任务 → 可靠执行单元 → 输出可信结果
                          ↑
             内部：Executor LLM + Reflector LLM 协作
```

对外它像一个"增强型 LLM"，输入任务，输出经过校验的结果；内部仍然由两个 LLM 分别负责执行和检查，保证客观性。

### LLM+ 增强单元

不只 Executor，每个外部角色都可以看作"核心 LLM + 补强 LLM"的组合：

| 角色 | 核心 LLM | 补强 LLM |
|---|---|---|
| Soul | 价值观判断 | 记忆 LLM（长期原则、底线案例） |
| Planner | 任务规划 | 记忆 LLM（历史规划经验、星序图索引） |
| Executor | 执行与推理 | Reflector LLM（检查输出） |
| Reflector | 质量审查 | 错误模式记忆 LLM |
| Coder | 代码生成 | 代码审查 LLM + 规范记忆 LLM |

核心思想是**用封装抵消 LLM 弱点**：不修改底层 LLM，而是给它叠加增强能力。每个角色对外是一个概念，对内是一个小网络。底层 LLM 升级时，增强层可以保留；增强 LLM 本身也能通过课程学习逐步变强。

### 器官类比

如果把增强后的 LLM 看作**器官**，agent 就是一个由多个器官协同工作的身体：

| 人体 | agent |
|---|---|
| 器官 | LLM+ 增强单元（Soul / Planner / Executor / Reflector / Coder） |
| 器官内部结构 | 核心 LLM + 补强 LLM |
| 血液循环 / 神经信号 | 角色间的消息、状态、执行上下文 |
| 大脑（整体协调） | Planner 编排层 + 各器官的协同调度 |
| 感官与手脚 | 工具（读文件、执行命令、查网页、发邮件） |
| 记忆系统 | memory-store 和各角色的记忆 LLM |
| 肌肉记忆 / 反射 | 星序图 |
| 训练成长 | 课程体系 |

这个类比的价值：

1. **功能分化自然**：每个器官只负责特定能力，不混在一起；
2. **内部复杂性被封装**：器官内部可以很复杂，但对外只提供明确功能；
3. **协同关系清楚**：器官之间不是互相替代，而是互相配合；
4. **成长和修复有依据**：课程就是训练器官能力，星序图就是形成肌肉记忆。

## 达成目标需要实现的功能

1. **执行可观测**：完整记录 AI 每次 loop 执行过程（工具调用序列、参数、结果、分支决策）。
2. **模式提取**：从一次成功执行中识别通用步骤。
3. **星序图建模**：把模式转化为 DAG/状态机（节点 + 边 + 参数化）。
4. **星序图执行引擎**：flow-engine 按图执行，处理节点、分支、错误、重试。
5. **匹配与复用**：新任务进来时，判断能否用已有星序图完成。
6. **验证与迭代**：用相似任务测试，对比直接执行的 token 消耗和成功率，持续优化。

## 课程体系

课程不脱离项目，跟着 agent / flow-engine 的开发进度走。

### 阶段一：会做事

| 课程 | 主题 | 实践任务 | 目标 |
|---|---|---|---|
| 1 | 用 loop 完成一次简单任务 | 用 chat-core 完成文件读取/分析 | 理解 ReAct 循环如何工作 |
| 2 | 观察和记录执行过程 | 记录一次任务的工具调用链、成功/失败节点 | 理解什么是可沉淀的经验 |

### 阶段二：会抽象

| 课程 | 主题 | 实践任务 | 目标 |
|---|---|---|---|
| 3 | 识别可沉淀的任务模式 | 判断哪些任务是一次性的，哪些能复用 | 理解模式识别 |
| 4 | 把执行转化为通用步骤 | 将具体任务转化为参数化步骤列表 | 理解抽象和参数化 |

### 阶段三：会建图

| 课程 | 主题 | 实践任务 | 目标 |
|---|---|---|---|
| 5 | 用 flow-engine 表达流程 | 用 JSON/YAML 描述一个简单工作流 | 理解星序图数据结构 |
| 6 | 设计分支和容错 | 为星序图添加 if/else、重试、错误回退 | 理解完整流程控制 |

### 阶段四：会进化

| 课程 | 主题 | 实践任务 | 目标 |
|---|---|---|---|
| 7 | 验证星序图效果 | 用新任务测试，对比直接执行的 token 和成功率 | 理解验证方法 |
| 8 | 星序图的匹配与复用 | 根据用户请求自动选择星序图 | 理解复用决策 |
| 9 | 与人类协作沉淀 | 何时请求人类确认，如何把反馈回写 | 理解可控进化 |

## 当前项目结合点

- 课程 1-2：基于现有 chat-core loop 和工具链；
- 课程 3-4：在开发 agent 的 Planner/Reflector 过程中实践；
- 课程 5-6：在实现 flow-engine 的过程中实践；
- 课程 7-9：在 agent 和 flow-engine 联调时实践。

## 待确认事项

1. **第一批课程从哪开始**：当前 flow-engine 和 skill-host 都是 scaffold，建议从已有 chat-core 能力开始，等 flow-engine 有基础执行能力后再进入建图阶段。
2. **星序图触发方式**：是 AI 主动发现"该沉淀了"，还是人类明确指令"把刚才的过程沉淀为星序图"？前者更自主，后者更可控，适合早期验证。
